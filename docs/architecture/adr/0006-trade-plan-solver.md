# ADR-0006: Расчёт плана сделок

Статус: Принято  
Дата: 29 июля 2026 года

## Контекст

План должен учитывать целевые доли, лоты, доступные позиции, деньги, комиссии и
несколько уровней предпочтений. Глобально оптимальное решение не требуется, но
результат обязан быть допустимым, объяснимым, воспроизводимым и достаточно
качественным.

## Решение

Для поиска плана используется Timefold Solver — pure JVM library без нативной
C++-зависимости.

- Все hard constraints должны быть выполнены: неотрицательный остаток, запрет
  продажи сверх позиции, целые лоты и отсутствие продаж в режиме только покупок.
- Уровни score последовательно учитывают отклонения от целевого распределения,
  комиссии, оборот и число операций. Точный порядок и tie-break rules являются
  частью доменной спецификации.
- Количество лотов моделируется ограниченным счётным диапазоном из позиции,
  доступных денег, цены и размера лота.
- Timefold скрыт за внутренним интерфейсом `TradePlanSolver`; его annotations и
  types не входят в доменную модель и публичный API `planning`.
- После solver отдельный доменный validator повторно проверяет результат и
  финансовые инварианты с `BigDecimal`.
- Используются фиксированный random seed, упорядоченные коллекции и
  детерминированное ограничение числом шагов. Ограничение только по времени не
  является основным условием остановки.
- Объяснение строится из доменных причин и вкладов constraints в score, а не из
  внутренних терминов Timefold.

Solver не обязан доказывать глобальную оптимальность. Он обязан вернуть допустимый
результат принятого качества либо явно сообщить, что результат не найден.

## Последствия

- Библиотеку можно заменить через реализацию `TradePlanSolver`.
- Детерминированные fixtures и property-based tests защищают от изменения
  качества при обновлениях.
- Одновременно в production выполняется не более одного solve.
- Настройка score является бизнес-решением, а не технической деталью адаптера.

## Рассмотренные альтернативы

- OR-Tools отклонён: JNI и native C++ усложняют сборку без нужды доказывать
  оптимальность.
- Choco Solver не выбран: Timefold естественнее выражает многоуровневые мягкие
  предпочтения и объяснение score.
- Собственный алгоритм отложен, поскольку потребовал бы самостоятельно
  реализовать поиск, улучшения, остановку и диагностику качества.
