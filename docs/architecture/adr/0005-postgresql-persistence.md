# ADR-0005: PostgreSQL и persistence

Статус: Принято  
Дата: 29 июля 2026 года

## Контекст

SQLite упростил бы первый запуск, но различия в типах, SQL и конкурентном
поведении создали бы отдельную миграцию на PostgreSQL. Для финансовых данных
важны точная десятичная арифметика, транзакции, миграции и одинаковое поведение
во всех окружениях.

## Решение

- Основная СУБД MVP — PostgreSQL 17. Самый новый major-релиз не является целью;
  production, локальная разработка и integration tests используют одинаковый
  major.
- Локально и в production PostgreSQL запускается отдельным Docker
  Compose-сервисом с постоянным volume.
- В integration tests Embedded PostgreSQL запускает настоящий PostgreSQL того же
  major из тестового процесса.
- Embedded PostgreSQL не используется в production.
- Схемой управляет Flyway; integration tests применяют настоящие миграции.
- Persistence использует синхронный JDBC, Kora JDBC repositories и явный SQL.

Финансовые значения хранятся как `numeric` без фиксированных precision и scale,
чтобы БД не округляла значение неявно. Идентификаторы хранятся как `uuid`,
временные метки — `timestamptz`, логические значения — `boolean`.

Допустимые диапазоны и scale проверяются Kotlin value objects и дублируются
безопасными `CHECK` constraints там, где это уместно. `Money`, `Price`, `Ratio`
и `CommissionRate` являются разными доменными типами. Округление разрешено
только в явно названных бизнес-операциях с указанным правилом; рыночные цены
сохраняются в исходной точности.

## Последствия

- SQL и миграции можно проверять на той же СУБД, что используется в production.
- PostgreSQL становится обязательной локальной зависимостью, кроме быстрых unit
  tests.
- Версия Docker image обновляется в рамках major 17 с проверкой backup/restore и
  миграций.
- Смена major или СУБД требует отдельного ADR.

## Рассмотренные альтернативы

- SQLite отклонён из-за различий в типах, SQL и последующей миграции.
- Embedded PostgreSQL в production отклонён из-за связанного жизненного цикла
  приложения и данных.
- ORM с неявно генерируемым SQL не выбран: явный SQL лучше подходит для
  контролируемых финансовых операций и небольшого домена.
