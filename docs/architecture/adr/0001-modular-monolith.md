# ADR-0001: Модульный монолит и архитектурные границы

Статус: Принято  
Дата: 29 июля 2026 года

## Контекст

MVP уже содержит несколько самостоятельных предметных областей. Общие
горизонтальные пакеты `domain`, `application` и `adapter` сделали бы владение
моделью и зависимости между контекстами неочевидными. Отдельные deployable
сервисы при однопользовательской нагрузке добавили бы несоразмерную сложность.

## Решение

Система реализуется как модульный монолит. Бэкенд остаётся одним Gradle-модулем,
а его верхний уровень организуется по вертикальным бизнес-модулям:

- `portfolio` — владельцы, портфели, позиции, деньги, цели и комиссии;
- `planning` — расчёт, редактирование и повторная проверка планов;
- `reporting` — семейная сводка и экспорт XLSX;
- `integration` — рыночные цены и брокерские позиции;
- `sharedkernel` — минимальный набор общих финансовых value objects;
- `bootstrap` — конфигурация, Kora graph и запуск приложения.

Корневой package — `io.familymoney`. Внутренняя форма бизнес-модуля:

```text
<module>
├── api
└── internal
    ├── domain
    ├── application
    └── adapter
        ├── inbound
        └── outbound
```

Пакеты создаются только при наличии содержимого. Другой модуль может обращаться
только к `<module>.api`; доступ к `<module>.internal..` извне запрещён.
Межмодульные зависимости задаются явным разрешённым списком и проверяются
ArchUnit.

```text
sharedkernel
    ↑
portfolio.api ← planning
              ← reporting
              ← integration

bootstrap → все модули
```

`sharedkernel` не зависит от бизнес-модулей и не превращается в пакет утилит.
`bootstrap` может видеть реализации всех модулей. Сгенерированные HTTP-типы
доступны HTTP-адаптерам, но не доменному и прикладному коду.

## Последствия

- Границы bounded contexts и разрешённые зависимости видны в package structure.
- Модули можно развивать независимо без операционной сложности микросервисов.
- ArchUnit-тесты являются обязательной частью `check`.
- Выделение модуля в отдельный сервис в будущем потребует явного нового решения.

## Рассмотренные альтернативы

- Микросервисы отклонены как избыточные для MVP.
- Общие горизонтальные слои верхнего уровня отклонены, поскольку скрывают
  владение предметной моделью.
- Несколько Gradle-модулей отложены до появления проблемы, которую нельзя
  надёжно контролировать package-границами и ArchUnit.
